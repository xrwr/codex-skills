# Summarizing Experiments Skill 設計

## 目的

実験の設定、成果物、評価結果を調べ、実験前に記録された仮説と実際の結果を対応付けて、簡潔な全体表と自己完結した個別サマリへ整理する配布可能なCodex skillを作る。

## 責務の分離

- `managing-experiments`は、実験開始前に検証可能な仮説、予想する変化、成否を判断する指標を記録する。
- `summarizing-experiments`は、記録済みの仮説を現在のconfig、resolved config、log、metric、prediction、最終成果物と照合し、結果を文書化する。
- 実験の起動、停止、再試行、GPU割当、設定所有権は`managing-experiments`の責務に残す。
- 仮説が事前記録されていない場合、結果からもっともらしい仮説を後付けしない。観測事実と、事後的な解釈または仮説候補を区別する。

## 出力

対象repositoryに既存の実験文書規約があれば、その保存先と形式を優先する。規約がない場合は、次を提案する。

```text
docs/experiments.md
docs/experiments/<experiment-id>.md
```

`docs/experiments.md`は全体サマリの正本とし、短い概要、必要な場合だけ系統図、主要結果表、未解決事項を持つ。個別ファイルは、仮説、親実験からの変更、評価条件、結果、解釈、次の判断を持つ。

## 主要結果表

標準形は5列に限定する。

| 実験 | 親 | 仮説 | 結果 | F1 |
|---:|---:|---|---|---:|
| 012 | 011 | 時系列入力でfalse negativeが減る | 反証。実データでは支持されなかった | 0.72 |

- `実験`と`親`には一覧表示用の短い数字IDだけを書く。repositoryの実IDが数字ならその値を優先する。非数字なら実IDとの対応を個別サマリに記録する。
- 非数字の実IDには既存の対応を再利用し、未割当の実IDだけに一意な数字IDを追加する。既存の数字IDは再番号付けしない。
- 最終列の見出しは`F1`に固定せず、対象実験の主指標名をそのまま使う。
- 指標セルには原則として絶対値だけを書く。親との差分、矢印、長い注釈を詰め込まない。
- 複数指標が結論に不可欠な場合だけ、`F1 / Recall`のように一つの列へまとめるか、表を目的別に分ける。
- 親が複数なら短い数字IDをカンマ区切りで書き、親がなければ`—`とする。
- `結果`は単なる数値の言い換えではなく、仮説に対する`支持`、`反証`、`判断保留`、`未評価`のいずれかが分かる短文にする。

## 証拠と状態

- configの存在、queueの完了、process終了、checkpointだけを実験結果として扱わない。
- 現在のattemptへ帰属する評価成果物と指標を優先する。
- 比較条件が揃わない場合は、優劣を断定せず`判断保留`とする。
- 実行中、失敗、未評価、成果物欠落を数値結果と混同しない。
- 事実、解釈、次に検証する仮説を分ける。

## 個別サマリ

個別サマリは次の順序を既定とする。

1. 要旨
2. 仮説と判定基準
3. 親実験からの変更
4. 評価条件と証拠
5. 定量結果
6. 定性的な改善・悪化または失敗分析
7. 結論と次の判断

学習データ例、prediction全文、config全文などは、その実験の結論を理解するために必要な場合だけ載せる。LLM、Kaggle、SFT、teacher、trace、特定のdirectory構造は必須化しない。

## Package

初期版は次の3ファイルに限定する。

```text
skills/summarizing-experiments/
├── SKILL.md
├── agents/openai.yaml
└── references/report-contract.md
```

`SKILL.md`は発火条件、コア原則、短いworkflow、Quick Reference、Common Mistakesを持つ。詳細な出力形式と例は`report-contract.md`へ分離する。scriptとassetは作らない。

## 検証方針

- スキルなしのagentが、結果から仮説を後付けする、queue完了を結果扱いする、横長の表を作る、ニモトロン固有形式を一般化してしまうscenarioをREDとして記録する。
- スキルありで同じscenarioを実行し、5列表、動的な指標見出し、絶対値のみの指標セル、証拠に基づく判定が守られることを確認する。
- package testでfrontmatter、3ファイル構成、portableな記述、表契約、`managing-experiments`側の事前仮説記録を検査する。
