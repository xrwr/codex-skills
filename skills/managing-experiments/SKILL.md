# Managing Experiments

## Overview

Experimentを仮説と検証計画の単位、trialを計画内の条件として管理する。実行履歴はjob ID・run ID・logで追い、人手のattempt採番・専用directoryを必須にしない。実験設定を自己完結させ、状態を対象実行の成果物で判定する。既存repositoryの契約を正本とし、実験管理を扱わない一般的な実装には適用しない。

新たに命名ルールを決める場合は、実験を`001`、条件を`001a`・`001b`・`001c`とする。英字は条件の違いに使い、fold・再実行では増やさない。詳細は[run lifecycleの条件ID](references/run-lifecycle.md#条件idの表記)に従う。

結果の記録には条件・状態・数値・観測・未確認事項を残し、事後の考察を混ぜない。事前仮説と承認済み計画はその記録時点を明示して保持する。考察はチャットで示し、実験結果から確認できる重要な比較結論は個別の許可を求めず短い知見として記録する。指定・規約がなければ知見は`docs/knowledge/`へ保存する。要約と知見の判定・粒度・人間の訂正の扱いは、利用可能なら`summarizing-experiments`に従う。未検証アイデアや裏付けのない原因説明・一般化の保存は具体案への許可を得る。

## 実験開始前の提案と確認

新しい実験や未承認の計画変更では、以下を具体化した実験案をチャットで提示し、ユーザーの確認を得てから実行する。「改善して」「次の実験を進めたい」という依頼では、まず具体的な仮説・条件・構成を提案する。具体的な計画や自動実験の範囲・予算がすでに許可されている場合は、下の判断基準に従い、範囲内の作業について毎回確認し直さない。

仮説を確認する単位は上位のexperiment（例：`001`）。新しい実験番号を提案するときは、番号の候補・名前・実験全体の仮説と根拠・比較計画を示し、「この番号と仮説で実験を開始してよいですか？」と確認する。`001a`・`001b`はその仮説を検証する条件であり、各trialに独立した仮説や仮説への承認を要求しない。trial追加では承認済みの上位仮説を短く再掲し、条件ID・変更条件・比較基準・検証上の役割を示す。追加条件や予算が未承認なら、その差分への確認を得る。

### 採番と確認の判断

承認された検証計画・条件と今回の差分を照合し、採番と実行の許可を別々に判断する。新しい番号は提案時に候補として知らせ、確認後に正式な実験として登録・実行する。具体的な番号・上位仮説・比較計画がすでに承認済みなら再確認しない。新experimentの採番と上位仮説の選定を含めて自律実行が明示的に許可されている場合も、番号と仮説を開始前に伝えて記録し、許可された範囲・予算内で進める。一般的な改善依頼や自動実験の回数指定だけを、その一括許可と扱わない。

| 今回の作業 | 採番・扱い |
|---|---|
| 起動ミス、保存先ミス、途中失敗からのやり直し | experiment・trial・foldを維持し、状態と実行履歴を更新する |
| 実装が計画どおりでなかったので直す | experiment・trial・foldを維持する。修正前の結果が無効なら理由を記録する |
| 同じ条件のcheckpointから再開 | 同じ条件の続きを実行し、再開元を記録する |
| 計画内で学習率・モデルなどの比較条件を追加 | 同じexperimentに次のtrialを追加する |
| 別の問いや比較計画を検証する | 過去の計画を検索し、該当するexperimentがなければ新番号の候補と上位仮説・比較計画を提示して確認する |
| 同じ軸の探索範囲・予算を広げる | 主仮説と固定条件が同じなら計画の変更として記録する。許可範囲外なら確認する |
| どれに当たるか判断できない、または許可範囲を超える | 判断に迷う差分・影響・選択肢を示して確認し、依存する実行は待つ |

「ミスを直して」「やり直せ」は、原則として対象IDを維持する修正・再実行の指示と解釈する。失敗、セッションの切替、コードの書き直しを採番理由にしない。修正は記録された意図どおりの条件に戻すことであり、都合のよい条件変更を修正と呼ばない。計画の意図を確定できない場合や比較の意味が変わる場合は、その差分を分類し直し、判断できなければ確認する。

許可された計画・自動実験の範囲・予算内では、この表で自律的に判断して理由を記録する。新experimentの扱いは上記の確認条件に従う。修正・再実行も実行回数・時間など合意した予算に数え、同じ条件だからという理由で上限を延長しない。投入前に対象jobと成果物を確認し、重複実行を防ぐ。

### チャットに出す実験提案フォーマット

開始前の提案は、次のフォーマットを実際の値で埋めてチャット本文に出す。冒頭の一文で何を確かめる実験かを伝える。ファイルに保存した計画は、その提案の詳細資料としてリンクする。

```markdown
次の実験を提案します。〈観測した課題〉を踏まえ、〈変更〉によって〈期待する結果〉になるかを確かめます。

| 項目 | 提案内容 |
|---|---|
| 実験番号・扱い | 〈新番号の候補または既存番号・名前〉／〈新experiment・trial追加・retryの別と理由〉 |
| 実験全体の仮説・根拠 | 〈上位experimentで予想する効果と根拠。既存experimentなら承認済み仮説を短く再掲〉 |
| 条件ID・役割 | 〈001a・001bなどのID、各条件が上位仮説の何を比較・検証するか〉 |
| 比較対象 | 〈基準experiment・trial・採用結果のjob／run ID・成果物〉 |
| 変更条件 | 〈各trialで変える値と、確かめること〉 |
| 固定条件 | 〈データ・split・モデル・学習条件など、比較間でそろえるもの〉 |
| 評価・判定 | 〈評価データ・主指標・期待方向または閾値〉 |
| Configs | 〈作成・変更するパス、形式、再利用する設定とtrial差分〉 |
| Outputs | 〈解決した保存先、trial・fold・実行履歴の対応、主要成果物〉 |
| 記録先 | 〈実験ドキュメント・実行記録・補助ログ・結果要約のパス〉 |
| 実行範囲・予算 | 〈trial数×fold数、GPU割当、試行数・時間等の上限〉 |

実行コマンド：〈実際のコマンドまたは投入wrapperと引数〉
確認済み：〈設定解決・基準との差分・出力先の検証結果〉
未確定：〈未確認事項や見積もりの不確実性。すべて確認済みなら「なし」〉

この番号と仮説・比較計画で実験を開始してよいですか？
```

各欄は短く具体的に書き、複数trialの条件は必要に応じて小さな表を添える。trial追加の確認では末尾を「この条件追加と実行範囲で開始してよいですか？」とし、承認済みの番号・上位仮説を再承認の対象にしない。仮説生成の探索では「実験全体の仮説・根拠」を「実験全体の探索目的・根拠」に置き換え、探索範囲と評価方法を記入する。Configsは既存entrypointが読む形式と配置にそろえ、共有設定の変更は既存実験への影響も添える。Outputsは条件・foldごとの保存先と、再実行時に旧結果を保持して混在を防ぐ方法を示す。

提案と確認の問いを出したら、ユーザーの返答を待つ。承認を受けた計画と範囲を実験記録へ保存し、その範囲の実行へ進む。

未承認の計画について確認を求める前に、既存構成の調査、必要なコード・config案の作成、設定解決・差分・出力先の静的検証まで行い、レビュー可能にする。その計画の承認を得てから、実験jobの投入（保留・予約を含む）、学習、本評価、実行用outputの作成へ進む。

未承認の仮説生成の探索を提案する場合は、探索目的・範囲・予算・評価方法を示して確認を得る。承認済みの具体的な計画や自動実験の許可範囲が会話にある場合は、その範囲の検証を判断表に従って継続する。仮説、比較条件、config／output構成、予算を承認範囲外へ変える場合は変更点を再提示する。状態確認・結果の読み取りは依頼に応じてそのまま進める。

## Workflow

1. Repository、config、scripts、tests、output、log、job stateを先に検査する。実在する契約と不明点を分ける。
2. 採番・計画時は[run lifecycle](references/run-lifecycle.md)のIdentityを読み、過去のexperimentも探して、trial追加・retry・新experimentを判別する。新番号の候補と上位仮説は開始前に伝え、上記の確認条件に従う。実験全体の仮説と根拠、比較対象、固定条件、変更軸・探索範囲、予算、評価方法と期待方向または閾値を既存の実験記録へ保存する。各trialには条件ID・変更条件・上位仮説の何を確かめるかを残し、独立した仮説を必須にしない。明示的な探索は同参照の規則に従う。
3. 未承認の計画は上記のフォーマットで提示し、承認の返答を待つ。すでに許可された計画・自動実験では判断表を適用し、範囲内なら計画と判断理由を記録して進める。Config schemaとpathはrepositoryの既存規約、またはユーザーと合意した構成にそろえる。
4. 過去runのstatus/result確認で事前仮説がなければ、記録済みの仮説生成の探索と記録の欠落を区別し、結果から事前仮説を後付けしない。
5. 入力、split、意味上の変更、必要成果物を特定する。
6. Config作成・変更では[config architecture](references/config-architecture.md)を読む。experiment configを自己完結したselection manifestにする。
7. 実行、retry/restart、status/result確認、W&B、複数GPUへの割当では[run lifecycle](references/run-lifecycle.md)を読む。experiment・trial・fold・実行履歴を照合し、資源割当と成果物のprovenanceを検証する。
8. 投入時は同参照に従って、単独検証または上限を定めた探索バッチの評価後に要約jobを登録する。補助記録は本実験のoutputツリーの外へ置く。
9. 変更範囲、確認済み証拠、未解決事項を報告する。依頼のないstart、stop、delete、submitを行わない。

Hydra、pueue、W&B、Lightningなどはrepositoryに既存し、現在利用可能な場合だけ使う。導入や必須化を推測しない。
