# Completion and Notification

## 要約と知見の役割

結果の記録には条件・状態・数値・観測・未確認事項を残し、事後の考察を混ぜない。事前仮説と承認済み計画はその記録時点を明示して保持する。考察はチャットで示し、実験結果から確認できる重要な比較結論は、短い本文・具体的な保存先と見出し・根拠を知見の追加案として提示し、その案へのユーザー承認後に記録する。既存知見の更新も変更案への承認を得る。指定・規約がなければ知見は`docs/knowledge/README.md`へ保存する。要約と知見の判定・粒度・人間の訂正の扱いは、利用可能なら`summarizing-experiments`に従う。未検証アイデアや裏付けのない原因説明・一般化の保存も具体案への許可を得る。

## Completion Summary

- 単独検証、または対象trialと上限を事前に定めた探索バッチの投入時に、必要な評価の完了後に結果を要約する段階を計画する。既存queue／schedulerで後続処理を管理する環境だけ要約jobを登録し、通常のコマンド実行なら評価終了後に同じ作業セッションまたは既存の要約方法で続ける。短い探索の各trial・各foldに要約jobを増殖させず、バッチの記録を集計して同じexperimentのサマリを更新する。バッチ完了をexperimentの仮説検証完了と同一視しない。要約不要の指定があれば省く。
- `summarizing-experiments`が利用可能なら要約方法を任せる。未導入でもPueueやCodex CLIの導入を要求せず、既存の要約方法で確認済み事実を記録し、自動要約連携は未設定と報告する。
- Promptは「実験042の結果をまとめて」程度の一文にする。再実行が複数あり対象が曖昧な場合だけ、既存のrun名や成果物のpathを足す。スキル本文の転記やprompt専用ファイルの作成は不要。
- 非対話の要約jobでは、未承認の知見・アイデアは保存せず、追加・更新案の本文・保存先・根拠を最終応答に残して終了する。ジョブログへの出力をユーザーへの通知済みと扱わない。後の対話で結果確認を依頼されたら未保存の案を再提示し、承認後に保存する。知見の承認待ちだけを理由に要約jobを失敗・待機扱いにしない。具体的な範囲の自動記録が明示的に許可された場合だけ、その範囲内で保存して本文と保存先を報告する。
- 対象trial・fold・採用結果のjob／run IDと成果物の集合と後続job IDを既存の実行記録へ残す。失敗trial・不足foldがあれば、その欠落を集計に残す。個別サマリと全体の系統図・一覧表、知見については承認済み案の保存または未承認案の応答への提示を確認して要約完了とする。要約jobから新たな実験を投入しない。

依頼なしにrunをstart/stopせず、outputやartifactをdeleteしない。破壊的操作が必要なら対象と影響を示して承認を求める。

## 任意通知の順序と境界

以下は外部通知を使う場合だけ適用する。通知先や対応adapterがなければこの節以降は省略でき、計画・実行・評価・要約は継続する。Pueue＋Discordの外部実装は[任意adapter](execution-adapters.md#pueueとdiscordの通知adapter)の一例で、他PCへの必須依存ではない。

通知は、保存先・宛先・送信項目について承認され、設定済みの場合だけ登録する。スキルやコードの準備を秘密保存・実送信・常駐有効化の許可と扱わない。全pueue jobを推測で通知対象にせず、競技を問わず、managing-experimentsから明示登録した今後の実験だけを扱う。コンペ名のallowlistを作らず、全jobや全repositoryを自動取り込みしない。

成功の順序は **本体 → 必要な評価集計 → summarizing-experiments → 成果物の帰属と保存確認 → 通知**。通知は独立watcherから送り、実験jobの成功依存先に送信jobを追加しない。通知障害で学習・評価・要約の終了コードを変えない。

- 開始通知は本体computeのRunningを観測した時に1通。投入・待機・helper・評価だけのRunningでは送らず、初回観測ですでに本体が終了済みなら遡って送らない。仮説・変更・割当資源は登録時に明示した情報だけを表示する。
- 学習・評価・起動helperの直接失敗は、要約を待たず最初の1件を失敗通知候補にする。DependencyFailedの連鎖やhelper成功は送らない。
- 要約だけが失敗したら、確認済み評価成果物があれば「実験完了・要約失敗」、なければ「要約失敗（評価成果物未確認）」とする。学習失敗と混同しない。
- summaryの終了コード0だけでは完了通知しない。下記の確認記録がない／根拠が変わった場合は `waiting_for_verified_artifacts` として保留する。
- 中止通知には本人による明示的な中止の記録が必要。Killedだけでは本人の中止と推測しない。
- 通知は既存のsummary単位（単独検証または上限を定めた探索バッチ）で開始1通＋終端1通を上限とし、別々に重複防止する。開始の配送失敗で終端通知を抑止しない。foldごとに増やさない。retryは同じexperiment／trialで新しい実行識別子へ登録する。

## 登録と確認記録

Pueue＋Discord adapterの処理は workflow.py（`lab-notify/experiment_notifications/workflow.py`）。既存投入コードや台帳を正本にし、全投入を置換しない。通知が設定済みの場合、今後作成・更新する投入wrapperで、job IDを既存台帳へ確定した後に `register` を呼び、結果を台帳と投入報告へ残す。登録エラー時に既存jobを停止・再投入しない。台帳から通知登録だけを復旧する。

`register` は、既存の `jobs.json`・`launch.json`、または役割を明示した汎用台帳からIDを取得する。人間に毎回job IDを入力させない。登録後のrun IDを台帳に残し、summary wrapperへ引き渡す。登録仕様とコマンドは [通知登録インターフェース](notification-interface.md) を参照。

通知が有効な今後のsummary wrapperでは、既存の短い要約依頼に「この実行の通知用成果物確認を行う」旨と台帳の場所だけを添え、この参照を読ませる。summarizing-experiments本文をpromptへ転記しない。既存の非対話ログ・セッションID記録を使う。他スキルを変更したり、現在稼働中のsummaryを差し替えたりしない。

成果物確認はsummarizing-experimentsとそのreport contractに従う。評価の位置づけ、採用したtrial／fold／job、resolved config・コード・データの対応、指標定義を確認する。完成した実験サマリ、task一覧／系統図、承認に応じた知見の扱いを確認し、指標改善と完了を混同しない。知見の記録不要や、未承認の知見・アイデアを応答に提示した場合も要約完了にできる。knowledge_contractはこの扱いの確認であり、未承認の知見保存を要求するものではない。

通知用の結論も同じ計画・判定契約に従う。事前仮説と基準、今回の操作、明示比較元、評価母集団・条件・不確かさを照合し、確認した短文だけをsummary確認記録のassessmentに渡す。Discord上の解釈と、実験レポートに保存する事実を区別し、通知のためにレポートへ事後の仮説を作らない。支持／不支持は評価が判定に十分な場合だけで、実行成功・要約成功を仮説支持と扱わない。判断保留／未評価／評価条件の不足は通知では「判断不能」として理由を明記する。数値の増減だけで判定を生成しない。

- 評価jobが終了した後、summary処理の冒頭などで確認できれば `attest --phase evaluation` を残す。評価job自身がまだRunningの間には記録しない。これにより後段の要約失敗を実験失敗と区別できる。確認処理をしていない評価へ、機械的に確認済みフラグを付けない。
- 要約完了前の最終処理、または完了後の確認で `attest --phase summary` を残す。run ID、採用compute／evaluation job集合、summary job・実セッションID、確認項目、成果物path・SHA-256を渡す。評価の確認を兼ねられるため、成功時に別のevaluation記録を必須にしない。
- 必須根拠は既存provenance、summaryでは実験サマリと一覧も含む。通知に指標を含める場合だけ、その指標ファイルも必須とする。知見記録は承認に基づいて実際に保存・更新した場合に根拠へ追加する。新しい人向けレポートや手書きの試行階層を増やさず、補助JSONは既存台帳の近くに置く。
- スクリプトはjob集合・job identity・ファイルhashを照合する。意味上の帰属や評価妥当性をhashから自動で証明するものではない。確認担当が既存証拠を読んだ上で記録する。根拠が更新されたら再確認してから記録を更新する。

## 通知テンプレート

表示定義は templates.json（`lab-notify/experiment_notifications/templates.json`）、描画は render_template.py（`lab-notify/experiment_notifications/render_template.py`）。固定順を使い、欠落項目は省く。

標準は通常テキスト1通で、Embedカードは使わない。タイトルは「▶️ 開始｜コンペ 実験名」「✅ 完了｜コンペ 実験名」「❌ 失敗｜コンペ 実験名」「⏹️ 中止｜コンペ 実験名」。✅は実行完了だけを示し、仮説支持を意味しない。完了はタイトル1行と仮説・結論・主指標・所要時間の箇条書き4行。`- **仮説**: ...` のようにラベルだけ太字、内容は同じ行、項目間空行なしとする。比較元・基準値・差を主指標へ、必要な根拠・解釈・評価制約を結論へまとめる。開始も同じ太字ラベル形式で短く表示する。

要約だけの失敗は「❌ 要約失敗（実験完了）」、評価成果物が未確認なら「❌ 要約失敗（評価成果物未確認）」とし、✅完了を付けない。開始通知の仮説・変更・割当資源・ETA、および完了通知の仮説・結論・主指標比較・実測時間の契約は表示を詰めても保持する。通知形式の変更を、既存投稿の編集や確認用投稿の送信許可と扱わない。

| 種類 | 表示順 |
|---|---|
| 開始 | コンペ・実験名 → 明示した仮説 → 変更点 → 実行先通称・割当GPUまたはCPU実行 → 所要時間範囲 → JST終了見込み |
| 完了 | コンペ・実験名 → 事前仮説 → 結論（支持／不支持／判断不能） ・必要な根拠と制約 → 主指標の今回値・比較元名と基準値・差分 → 実測所要時間 |
| 失敗 | コンペ・実験名（要約だけの失敗は区別） → 段階 → 確認済み理由／原因未確認 → 時間 → job ID |
| 中止 | コンペ・実験名 → 段階 → 確認済み理由 → 時間 → job ID |

コンペ名、主指標キーと表示名は登録時に明示する。主指標未設定なら「未確認」とし、順位だけで指標を選ばない。今回値は確認した結果ファイル内の登録済み有限数値だけ。比較元の実験・条件名と値を明示し、評価母集団・条件の比較可能性を照合した場合だけ差分を表示する。比較不明なら「比較: 未確認」とし、ゼロ差や前回比を推測しない。既存の競技別 profileは任意の表示例で、競技の制限ではない。Gold等の独立性の制約は残す。実測時間は本体の最初の開始から終端まで、確認できなければ未確認とする。fold数・要約完了等の運用情報は成功本文へ出さない。任意のレポートリンクが実ファイルと閲覧先の照合を通った場合だけ、末尾へ「📄 レポートを開く」を1行添える。

仮説・結論・比較根拠は明示確認済みの限定フィールドだけを送る。未知JSONの全キー・ログ・command・環境変数・内部path・例外文字列を転送しない。確認済みassessmentがなければ「判断不能」と不足条件を表示し、未確認の解釈で埋めない。送信するcontentをescape後・UTF-16相当で2000文字以内に確認する。ラベル以外のMarkdown特殊文字をescapeし、allowed_mentionsとTTSは無効。詳細は[完了結論の契約](notification-interface.md#完了結論の契約)を参照。

開始の所要時間は確認済み計画・履歴に基づく、本体から評価・要約までの範囲だけ。根拠そのものは本文へ表示せず、根拠なし／対象範囲不明なら所要時間と終了見込みは「未定」。年月日付きJSTで日付跨ぎも示す。資源は明示された通称・GPUモデル・割当数・番号、またはCPU実行だけで、不明な項目は省略する。使用量やIPを送らず、group名からGPUを推測しない。詳しい入力契約は[開始通知の契約](notification-interface.md#開始通知の契約)を参照。

## 独立watcherと移行

Pueue＋Discord adapterのwatcherは60秒ごとに `pueue status --json` だけを読み、SQLiteで登録・確認記録・送信状態を永続化する。job ID再利用をcreated_at／label／pathで検出し、不一致や削除時は推測しない。送信前にclaimを保存するため重複を抑制できるが、送信途中の停止・応答不明では欠落しうる。自動再送せず到着を本人が確認する。

既定の設定は無効。保存先は `~/.config/experiment-notify/`（0700、秘密と設定0600）、台帳は `~/.local/state/experiment-notify/workflow.sqlite3`（親0700、ファイル0600）。秘密は本人TTYの既存helperから入力し、チャットやargvへ貼らない。user systemd serviceの例は準備物で、承認前にインストール／起動しない。pueue callbackやdaemon再起動は不要。WSL起動後の復帰とWindowsからのWSL自動起動は区別する。

各PCの連携導入は、そのPCで承認した開始時刻以後に投入する新規実行から。既存監視中の実験を取り込んで重複通知せず、過去jobの一括取込や設定の暗黙有効化を行わない。有効な設定・秘密・送信台帳はホストローカルで、skillとともに他PCへコピーしない。

Atlasリンクは[任意のAtlasレポートリンク](notification-interface.md#任意のatlasレポートリンク)に従う。確認済みsummaryのreport artifactを使い、リンク不成立だけで完了通知を保留しない。Atlas未導入PCには連携を要求しない。
