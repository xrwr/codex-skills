# Planning and Approval

## Identity

| 単位 | 意味 |
|---|---|
| experiment | 実験全体で判断する仮説と、その検証計画。複数trialを通じて結論を出す |
| trial | 検証計画内の具体的な条件。設定・seedなどの組合せを特定する |
| fold | 決めたCV計画の内訳。fold違いだけではtrialを増やさない |

テーマ名・テーマIDを必須の管理階層として追加しない。以下のID名・表記は例であり、repositoryの既存schemaを優先する。

実行履歴はjob ID・run ID・log・設定snapshotで識別する。人手のattempt採番・専用directoryを必須にしない。既存repositoryがattemptを使う場合は、その契約と過去の記録を保持する。

### 条件IDの表記

新たに命名ルールを決める場合は、experimentの3桁の数字IDに小文字の英字を付けてtrialを識別する。実験`001`の条件は`001a`・`001b`・`001c`、実験`002`の最初の条件は`002a`とする。条件名は`001a_baseline`・`001b_lr_half`のように短く添えてよい。`z`の次が必要なら`aa`・`ab`と続ける。

条件を追加するときに次の英字を割り当て、fold違いや同条件のretryではtrial IDを維持する。通常の保存先は`outputs/001/001b/`、CVありなら`outputs/001/001b/fold-0/`とし、実行回の番号を階層に追加しない。旧結果の保持と実行の識別は[実行記録・Retry Procedure](run-lifecycle.md)に従う。

チャット・条件表・結果表・比較基準の参照では`001b`のようにexperimentと条件を一つのIDで示す。設定・台帳ではexperimentとtrialの項目を保ち、この方式を採用する新規schemaなら`experiment_id: "001"`・`trial_id: "001b"`とする。既存のschema・ID・成果物は保持し、表記変更だけを理由に移動・改番しない。既存repositoryへ導入する場合は、config・出力先・loggerの対応を確認して対象範囲を決める。

### 仮説と検証計画

仮説は観測や既知の根拠から立て、何が成り立つと予想し、どの比較結果なら支持・不支持・保留かを開始前に記録する。実験全体の主張と、次のtrialを選ぶ局所的な予想を区別する。「係数0.01ならよさそう」という予想や先例の細かい実験YAMLだけを根拠に採番しない。

計画には比較対象、固定条件、具体的な変更軸・探索範囲、試行数や時間の予算、評価方法・判定条件を持たせる。「性能改善全般」のような無制限の範囲にしない。開始前の仮説の確認はexperiment（`001`）単位で行い、trial（`001a`・`001b`）単位では独立した仮説や仮説への承認を必須にしない。trialごとに条件ID、上位仮説の何を確かめるか、比較基準と変更条件を残す。上位仮説・比較計画が変わる場合は、trial追加として進める前に採番の判断へ戻る。

仮説生成を目的とする明示的な探索では、探索目的・範囲・予算・評価方法を事前記録し、各候補に根拠のない方向仮説を作らない。探索で得た傾向と、その後の仮説検証を区別する。通常の仮説検証を、記録を省くために探索と呼び替えない。

### 採番の判断

新しいexperimentを作る前に、最新だけでなく過去の実験記録を仮説・比較対象・検証範囲から検索する。

[採番と確認の判断](#採番と確認の判断)を適用する。新番号の候補を理由・実験全体の仮説・比較計画とともに開始前にユーザーへ知らせ、同参照の確認条件を満たしてから正式登録・実行する。「ミスを直して」「やり直せ」では対象experiment・trial・foldを維持し、失敗だけを理由に新IDを発行しない。動作確認や実装不具合の切り分けは対象実験の補助記録とする。固定条件や比較の意味を意図的に変える場合は、該当する既存計画がなければ新experimentとし、基準trial・成果物を記録する。採番が必要かと、実行が許可されているかは別に確認する。

変更の大小・実行時間・コードの行数で判断しない。層数3→4が002の計画内なら、最新が030でも002にtrialを追加する。一方、031が複数モデル方式を比較する計画なら、大きな方式変更も031内の候補である。その候補を独立して調整する032は`031b`など具体的な出発点へ紐付ける。元trialの移動・改番や、trialの下への無制限なtrial階層の追加は不要。

古いexperimentに戻る場合は、基準trial、コード版、resolved config、入力・split・評価方法を復元して比較可能性を確認する。現在のdefaultsやコードを暗黙に混ぜない。固定条件の変更を採用する場合はその比較計画を別experimentとして扱い、必要な基準の再評価を行う。過去の仮説・結果・IDは保持し、今回追加する計画を当時の事前記録として扱わない。旧記録にtrialがなければ基準条件への対応を今回記録し、成果物を推測で再番号付けしない。

## 実験開始前の提案と確認

新しい実験や未承認の仮説変更では、実験設定の作成前に仮説を確認する。ユーザーに検証したい仮説を尋ねるか、既存の観測を根拠にAIが仮説案をチャットで提示し、その案への承認を得る。「改善して」「次の実験を進めたい」という依頼だけで仮説を確定して設定を作らない。具体的な仮説・計画がすでにユーザーから指定・承認されていれば、その範囲で設定を作成し、同じ仮説を再確認しない。自動実験も下の判断基準に従う。

### 設定作成前の仮説確認

既存docs・config・コード・成果物の読み取り調査で、課題・既存計画・比較可能性を確認する。仮説が未定なら「今回検証したい仮説を教えてください」と尋ねるか、仮説案・根拠・比較対象・変更する要因・評価と判定方法を短く提示する。新experimentなら番号と名前の候補も添え、「この番号と仮説・比較方針で実験設定を作成してよいですか？」と確認する。ユーザーが判断するために必要な条件案や予算はチャットで具体化し、作成予定のconfig／outputのパスも示してよい。設定解決や新規ファイルの完成を、この確認の前提にしない。

仮説確認前は、新しいexperiment／trialのconfig、override、探索条件ファイル、実験用コードを作成・変更しない。一時ファイルのconfig案も同じ扱いとし、設定を作り終えてから仮説を提示する順序にしない。ユーザーの返答を待ち、確認に依存しない既存資料の調査は進めてよい。

確認後に承認された仮説・比較計画を記録し、必要な設定・コードを作成して静的検証する。仮説の承認と実行許可は区別する。仮説だけが確認され、条件や予算・実行が未承認なら、設定と検証結果を示して残る実行範囲の確認を得る。仮説・具体的な計画・実行範囲まで承認済みなら再確認せず進める。設定の具体化で仮説・比較の意味や承認範囲が変わる場合は、変更前に差分を提示する。

仮説を確認する単位は上位のexperiment（例：`001`）。`001a`・`001b`はその仮説を検証する条件であり、各trialに独立した仮説や仮説への承認を要求しない。trial追加では承認済みの上位仮説を短く再掲し、条件ID・変更条件・比較基準・検証上の役割を示す。追加条件や予算が未承認なら、設定の作成・変更前にその差分への確認を得る。承認済み計画内のtrial追加や同条件のretryでは仮説を再確認しない。

### 採番と確認の判断

承認された検証計画・条件と今回の差分を照合し、採番と実行の許可を別々に判断する。新しい番号は設定作成前の提案時に候補として知らせ、仮説・比較方針の確認後に正式な実験として登録する。実行にはその範囲の許可も必要とする。具体的な番号・上位仮説・比較計画がすでに承認済みなら再確認しない。新experimentの採番と上位仮説の選定を含めて自律実行が明示的に許可されている場合も、番号と仮説を設定作成前に伝えて記録し、許可された範囲・予算内で進める。一般的な改善依頼や自動実験の回数指定だけを、その一括許可と扱わない。

| 今回の作業 | 採番・扱い |
|---|---|
| 起動ミス、保存先ミス、途中失敗からのやり直し | experiment・trial・foldを維持し、状態と実行履歴を更新する |
| 実装が計画どおりでなかったので直す | experiment・trial・foldを維持する。修正前の結果が無効なら理由を記録する |
| 同じ条件のcheckpointから再開 | 同じ条件の続きを実行し、再開元を記録する |
| 計画内で学習率・モデルなどの比較条件を追加 | 同じexperimentに次のtrialを追加する |
| 別の問いや比較計画を検証する | 過去の計画を検索し、該当するexperimentがなければ新番号の候補と上位仮説・比較計画を提示して確認する |
| 同じ軸の探索範囲・予算を広げる | 主仮説と固定条件が同じなら計画の変更として記録する。許可範囲外なら確認する |
| どれに当たるか判断できない、または許可範囲を超える | 判断に迷う差分・影響・選択肢を示して確認し、依存する実行は待つ |

「ミスを直して」「やり直せ」は、原則として対象IDを維持する修正・再実行の指示と解釈する。失敗、セッションの切替、コードの書き直しを採番理由にしない。修正は記録された意図どおりの条件に戻すことであり、都合のよい条件変更を修正と呼ばない。計画の意図を確定できない場合や比較の意味が変わる場合は、その差分を分類し直し、判断できなければ確認する。

許可された計画・自動実験の範囲・予算内では、この表で自律的に判断して理由を記録する。新experimentの扱いは上記の確認条件に従う。修正・再実行も実行回数・時間など合意した予算に数え、同じ条件だからという理由で上限を延長しない。投入前に対象jobと成果物を確認し、重複実行を防ぐ。

### 仮説確認後の詳細な実験提案フォーマット

設定作成前の仮説確認は上記の短い提案で行う。確認後に実行範囲の追加承認が必要な場合は、次のフォーマットを実際の値で埋めてチャット本文に出す。冒頭の一文で何を確かめる実験かを伝える。ファイルに保存した計画は、その提案の詳細資料としてリンクする。未承認の仮説について、この表を埋めるために設定を先に作らない。

```markdown
次の実験を提案します。〈観測した課題〉を踏まえ、〈変更〉によって〈期待する結果〉になるかを確かめます。

| 項目 | 提案内容 |
|---|---|
| 実験番号・扱い | 〈新番号の候補または既存番号・名前〉／〈新experiment・trial追加・retryの別と理由〉 |
| 実験全体の仮説・根拠 | 〈上位experimentで予想する効果と根拠。既存experimentなら承認済み仮説を短く再掲〉 |
| 条件ID・役割 | 〈001a・001bなどのID、各条件が上位仮説の何を比較・検証するか〉 |
| 比較対象 | 〈基準experiment・trial・採用結果のjob／run ID・成果物〉 |
| 変更条件 | 〈各trialで変える値と、確かめること〉 |
| 固定条件 | 〈データ・split・モデル・学習条件など、比較間でそろえるもの〉 |
| 評価・判定 | 〈評価データ・主指標・期待方向または閾値〉 |
| Configs | 〈作成・変更するパス、形式、再利用する設定とtrial差分〉 |
| Outputs | 〈解決した保存先、trial・fold・実行履歴の対応、主要成果物〉 |
| 記録先 | 〈実験ドキュメント・実行記録・補助ログ・結果要約のパス〉 |
| 実行範囲・予算 | 〈trial数×fold数、GPU割当、試行数・時間等の上限〉 |

実行コマンド：〈実際のコマンドまたは投入wrapperと引数〉
確認済み：〈設定解決・基準との差分・出力先の検証結果〉
未確定：〈未確認事項や見積もりの不確実性。すべて確認済みなら「なし」〉

この条件と実行範囲で実験を開始してよいですか？
```

各欄は短く具体的に書き、複数trialの条件は必要に応じて小さな表を添える。trial追加の確認では末尾を「この条件追加と実行範囲で開始してよいですか？」とし、承認済みの番号・上位仮説を再承認の対象にしない。仮説生成の探索では「実験全体の仮説・根拠」を「実験全体の探索目的・根拠」に置き換え、探索範囲と評価方法を記入する。Configsは既存entrypointが読む形式と配置にそろえ、共有設定の変更は既存実験への影響も添える。Outputsは条件・foldごとの保存先と、再実行時に旧結果を保持して混在を防ぐ方法を示す。

仮説確認の問いを出したら、ユーザーの返答を待ってから設定作成へ進む。実行範囲の追加確認を求めた場合も、返答を待ってからその範囲の実行へ進む。

設定作成前の仮説確認と、設定作成後の実行前検証を区別する。仮説確認後に必要なコード・configを作成し、設定解決・差分・出力先の静的検証を行う。実行範囲の承認と検証結果を確認してから、実験jobの投入（保留・予約を含む）、学習、本評価、実行用outputの作成へ進む。

未承認の仮説生成の探索を提案する場合も、設定作成前に探索目的・範囲・予算・評価方法を示して確認を得る。承認済みの具体的な計画や自動実験の許可範囲が会話にある場合は、その範囲の検証を判断表に従って継続する。仮説、比較条件、config／output構成、予算を承認範囲外へ変える場合は、変更前に差分を再提示する。状態確認・結果の読み取りは依頼に応じてそのまま進める。
